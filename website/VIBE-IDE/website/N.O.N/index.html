Why N.O.N.

Compact, typed, deterministic. Zero deps. Browser/Node ready.

Compact

Fewer quotes/braces; arrays by dashes; optional inline arrays. Typical 25–45% token savings vs JSON.

Component-Aware

Inline components: Type(a:1) → {__type:"Type", a:1}. Perfect for schema hints and codegen.

LLM-Friendly

Readable, minimal, and deterministic. Great for prompts, embeddings, and memory stores.

Feature Snapshot

Core

  • Objects/arrays via indent + dashes
  • Components with __type mapping
  • Token-light strings (quote only when needed)
  • Comments with #
  • Browser/Node module (`non.js`)

Bridges

  • JSON ↔ N.O.N. round-trip
  • CML envelope bridge (Imaginatorium)
  • Component hinting for codegen/types
  • Drop-in for RAG/prompt payloads

N.O.N. vs JSON vs TONL

Positioned against TONL’s token-optimized pitch (tonl.dev): N.O.N. stays human-first, type-friendly, zero-deps, and easy to embed.

Format Token Savings Types/Components Streaming LLM Prompt Friendly Deps
N.O.N. 25–45% vs JSON (typical configs) Inline components → __type Line/indent friendly; can stream by line Yes (minimal syntax, human-readable) 0 (single JS file)
JSON Baseline No Yes Verbose; high token overhead 0
TONL 32–50% vs JSON; claims up to 60% with optimizations [tonl.dev] Type hints; table-like headers Yes (streaming, indexes) LLM-optimized; custom prompt needed TS package/CLI

N.O.N. aims for simplicity and embeddability over maximum compression. If you need heavy optimization/queries, see TONL; if you need human-first, typed, zero-dep payloads, use N.O.N.
